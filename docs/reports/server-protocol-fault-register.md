# Server and Protocol Fault Register

This is a client-facing backlog of confirmed server/protocol inconsistencies found while implementing Godot parity with the Python client. It records observed contracts, current client workarounds, and the change needed to unblock full workflows. It does not authorize or include server changes. Re-verify each item against the current handler and schema before fixing it.

## Open faults

| ID | Fault and evidence | Current client impact | Suggested server/protocol correction |
| --- | --- | --- | --- |
| API-01 | `sector.info` ship records contain `ship_id` and `name`, but omit hull identity. `db_ships_at_sector_json` in `src/db/repo/repo_cmd.c` constructs the records. | Godot uses a generic vessel for all other ships and does not guess from names or issue N+1 inspections. | Include the mechanical ship type and preferably a stable visual key such as `ship_type.code` in every visible-ship record. Keep art filenames and pixel data client-owned. |
| API-02 | `ship.inspect` schema requires `ship_id`, but `cmd_ship_inspect` in the ship command handler reads optional sector context and returns sector-wide ships rather than inspecting the requested vessel. | Single-ship details are disabled in Godot; selecting a ship does not imply supported inspection. | Make the handler consume and validate `ship_id`, require the vessel to be visible/inspectable in the current sector, and return a documented per-ship response; align the schema and protocol docs. |
| API-03 | `subscribe.add`/`subscribe.remove`: protocol docs and handlers use `topic`; strict schemas require `event_type` and reject unknown fields. | Godot does not submit add/remove requests or invalid automatic subscriptions. Subscription list/catalogue remain available. | Choose one field name and payload, update handler, schema, protocol docs, and tests together. |
| API-04 | `player.computer.recommend_routes` schema types `require_two_way` as boolean, while the handler reads it through an integer-only accessor. | Godot omits the filter and labels that server default behavior is used. | Make handler and schema use the same boolean representation and test true/false values. |
| API-05 | `move.pathfind` schema requires `from_sector_id`/`to_sector_id`; its handler reads `from`/`to` (or legacy `sector_id`) and does not consume `to_sector_id`. | Godot avoids the unusable operation and uses the compatible read-only autopilot route response as a planner; movement remains a separate explicit warp. | Align schema, handler, and documentation on one request shape and define whether pathfinding is read-only. |
| API-06 | `chat.send` schema requires `channel`/`message`, while its handler requires a recipient (`to_player` or `to_id`) and `message`; strict validation prevents supplying both shapes. | Private messages are visibly unavailable; public `chat.broadcast` remains available. | Define a recipient addressing contract, align the strict schema and handler, and document authorization/error behavior. |
| API-07 | `mail.send` schema requires `to_player_name`, while the handler reads `to` or `to_id`. `mail.delete` schema requires `mail_id`, while the handler expects an `ids` array. | Sending and deleting mail are disabled in Godot. Inbox/read remain available. | Align each schema with the implemented handler (or vice versa), document whether batch deletion is supported, and add contract tests. |
| API-08 | `mail.read` schema requires `mail_id`, while the handler reads `id`. | Godot currently sends both keys as a compatibility bridge; this relies on the schema allowing extra fields for this command. | Select one canonical key and align schema, handler, docs, and tests. |
| API-09 | `ship.rename` schema accepts `name`, while its handler requires `ship_id` and `new_name`. | Ship rename is disabled in Godot. | Define whether the active ship ID is implicit or explicit, then align schema and handler with one name field. |
| API-10 | `ship.jettison` strict schema requires numeric `commodity_id`, but its shared `cmd_trade_jettison` handler reads string `commodity`; the Python workflow sends the latter. The separate `trade.jettison` schema correctly matches the handler. | Python's legacy `ship.jettison` request is rejected; Godot uses the compatible `trade.jettison` command and has a regression test for `{commodity, quantity}`. | Align the `ship.jettison` schema with the shared handler or change the handler and Python client to a canonical commodity identifier. |
| API-11 | Port responses expose a legacy numeric `type`; StarDock is currently recognized by legacy type 9. Data-driven/custom port kinds have no stable semantic capability in the client-facing payload. | Tavern entry and shipyard access can be checked for known legacy kinds only; names are not used to infer capabilities. | Add a stable port-kind code and explicit capabilities (for example `has_tavern`, `supports_shipyard`) to authoritative port information. |
| API-12 | Insurance policy list, purchase, and claim handlers return hard-coded stub responses and do not operate on authoritative policies. | Godot presents insurance options as unavailable rather than implying they work. | Implement persistent policy/claim behavior and authoritative responses, then publish the request/response contract. |

## Resolution policy

- Treat each entry as open until a handler/schema/protocol change and a regression test demonstrate alignment.
- Keep client workarounds explicit; never guess missing gameplay identity from names or artwork.
- Do not alter the server or database as part of Godot-only implementation slices without a separately approved scope.
